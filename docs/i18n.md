# Internationalization (i18n) — Bilingual EN/VI Architecture

**Last Updated**: 2026-05-21 (Bilingual Phase 6 — QA & Locale Polish Complete)

## Overview

WORLDSCOLIDE supports English (en) and Vietnamese (vi) via **i18next + react-i18next**, with device-level language preference stored in `localStorage`. Language is a device setting (one across all save slots), not per-save.

**Key principle**: Source language is *asymmetric*. Most game data is English-authored (missions, items, enemies, etc.), but `civilization-config.ts` and `skills.ts` are Vietnamese-authored. The localization resolver overlays the target language from JSON and falls back to the source language inline.

---

## Architecture

### Two-Namespace Strategy

**`ui` namespace** (default — interface chrome)
- English source of truth: `src/i18n/ui.en.json` (708 keys)
- Vietnamese overlay: `src/i18n/ui.vi.json` (708 keys)
- **Key convention**: `<feature>.<section>.<element>` — e.g. `questBoard.title`, `roster.status.on-quest`, `tavern.recruits.cost-label`
- Enum/status labels keyed off raw data values: `status.${member.status}` → `status.idle`, `status.on-quest`, etc.
- **Usage**: `const { t } = useTranslation(); t('feature.x')`
- **Parity enforced**: `src/i18n/ui-parity.test.ts` fails if EN and VI key counts diverge. 708 keys each.

**`content` namespace** (game-data display + narrative)
- Game-data names/descriptions/zones + dialog/tutorial narrative
- **Key convention**: `<category>.<id>.<field>` — e.g. `missions.slime-extermination.name`, `items.pine-wood.description`
- **Source-language asymmetry** (the critical detail, documented below)
- **Usage**: Never call raw; use typed wrappers (see Contributors Guide below) or `tContent(category, id, field, fallback)`
- **Coverage enforced**: `src/i18n/content-coverage.test.ts` fails if required translations missing

### Source-Language Asymmetry (EN-authored vs. VN-authored)

The same entity can be sourced from different authoring languages. This is why the `content` namespace resolves differently than `ui`.

**EN-authored data** (most entities):
- Inline data string = English (source of truth)
- Vietnamese keys live in `content.vi.json`
- Fallback (when VI key missing) = inline EN value

**Examples**: Missions, items, enemies, equipment, furniture, facilities, recipes, archetypes, ranks, civ.role (despite being in civilization-config)

```typescript
// In src/game/data/missions.ts (EN-authored):
const MISSIONS = [
  { id: 'slime-extermination', name: 'Slay the Slimes', ... }
];

// In src/i18n/content.vi.json:
{ "missions": { "slime-extermination": { "name": "Tiêu diệt những Slime" } } }

// Call via wrapper (never inline):
missionName(mission)  // returns VI if available; fallback to inline EN
```

**VN-authored data** (civilization + skills):
- Inline data string = Vietnamese (source of truth)
- English keys live in `content.en.json` (sourced from lore glossary)
- Fallback (when EN key missing in content.en.json) = inline VN value

**Examples**: `CIV_CONFIG.displayName`, `.description`, `.passive.name/description`; `skills` all fields

```typescript
// In src/game/data/civilization-config.ts (VN-authored):
const CIV_CONFIG = {
  LinhSon: { displayName: 'Linh Sơn', ... }
};

// In src/i18n/content.en.json:
{ "civ": { "LinhSon": { "name": "LinhSon" } } }  // from lore-glossary.md

// Call via wrapper (never inline):
civName('LinhSon')  // returns EN if available; fallback to inline VN
```

**Mixed** (civ.role):
- Role values are *English text* despite being in civilization-config (VN-authored file)
- Treated as EN-authored: Vietnamese keys in `content.vi.json`

### Critical Config Detail: `fallbackLng: false`

When resolving content namespace keys, `tContent()` explicitly passes `fallbackLng: false`:

```typescript
export function tContent(
  category: string, id: string, field: string, fallback: string,
): string {
  return i18n.t(`${category}.${id}.${field}`, {
    ns: 'content',
    defaultValue: fallback,    // inline source-language value
    fallbackLng: false,         // CRITICAL: disable language fallback
  });
}
```

**Why this matters**: The global i18n init sets `fallbackLng: 'en'` (safety net for `ui` namespace). Without `fallbackLng: false` in content lookups:
- A Vietnamese player looks up a VN-authored entity (e.g., civilization name)
- The VI key is intentionally *absent* in `content.vi.json` (because the VN inline value is the source)
- Without `fallbackLng: false`, the resolver would fall back to the EN key in `content.en.json` and return English to a Vietnamese player
- With `fallbackLng: false`, the resolver goes active language → defaultValue (inline VN), which is correct

The UI namespace keeps the global EN fallback as a safety net for any un-migrated chrome strings.

### Language Preference (Device-Level)

**Storage**: `localStorage['settings.lang']` (not in save payload)

**Hook**: `useLanguage()` in `src/i18n/use-language.ts`
```typescript
export function useLanguage(): { language: Lang; setLanguage: (lang: Lang) => void } {
  const { i18n } = useTranslation();
  const language: Lang = i18n.language === 'vi' ? 'vi' : 'en';
  const setLanguage = (lang: Lang) => {
    void i18n.changeLanguage(lang);
    try { localStorage.setItem('settings.lang', lang); } catch { /* SSR */ }
  };
  return { language, setLanguage };
}
```

**Read before init**: In `src/i18n/index.ts`, language is read on app start via `readStoredLang()` and passed to `i18n.init({ lng })` so the first paint is already in the correct language (no flash EN → VI).

**Runtime change**: `i18n.changeLanguage('vi')` triggers React re-renders via the `languageChanged` event; all consuming components re-render automatically.

---

### Number Formatting

Intentionally left as en-US / locale-as-is (pixel-art HUD consistency). `formatGold()` and stat displays use bare `.toLocaleString()` per browser locale, not overridden.

**Known consideration** (user decision pending): Some platforms may want to use `.toLocaleString('vi-VN')` for Vietnamese users and `.toLocaleString('en-US')` for English players. Currently, formatting is global and not language-aware.

---

### Dev-Time Helpers

**`saveMissing` + `missingKeyHandler`** in `src/i18n/index.ts`:
- Enabled in dev (when `import.meta.env.DEV === true`)
- Warns on missing `ui` namespace keys to console the moment they are requested
- Disabled for `content` namespace (resolves source language via defaultValue by design — no false positives)
- In prod, no overhead, no console noise

```
└── content-coverage.test.ts      # Guard: ensures all entities have required overlay entries
```

## Contributors Guide: Adding a Translated String

### Case 1: UI Chrome String

Add a new interface label, button, or panel heading.

1. **Add key to BOTH** `ui.en.json` and `ui.vi.json` with the same path:
   ```json
   // ui.en.json
   { "myFeature": { "action": { "submit": "Submit" } } }
   
   // ui.vi.json (exact same key)
   { "myFeature": { "action": { "submit": "Gửi" } } }
   ```

2. **Call in React component**:
   ```typescript
   const { t } = useTranslation();
   return <button>{t('myFeature.action.submit')}</button>;
   ```

3. **Run tests**:
   ```bash
   npm run test
   # ui-parity.test.ts validates key counts match (708 each)
   ```

---

### Case 2: Game-Data Display Field

A new item, mission, enemy, skill, etc., where the name/description needs localization.

**Path A (EN-authored data — most cases)**:

1. **Add inline EN value** in the data file (e.g., `src/game/data/items.ts`):
   ```typescript
   const ITEM_DATABASE: Record<ItemID, Item> = {
     'my-sword': { name: 'Shiny Sword', description: 'A very shiny sword.', ... }
   };
   ```

2. **Add Vietnamese overlay** in `src/i18n/content.vi.json`:
   ```json
   { "items": { "my-sword": { "name": "Thanh Kiếm Sáng", "description": "Một thanh kiếm rất sáng." } } }
   ```

3. **Call via typed wrapper** in React:
   ```typescript
   import { itemName, itemDescription } from '@/i18n/content-wrappers';
   
   return (
     <div>
       <h2>{itemName(itemId)}</h2>
       <p>{itemDescription(itemId)}</p>
     </div>
   );
   ```

4. **Never call** `item.name` directly in the render path.

**Path B (VN-authored data — civ + skills)**:

1. **Add inline VN value** in the data file (e.g., `src/game/data/civilization-config.ts`):
   ```typescript
   const CIV_CONFIG = {
     MyFaction: { displayName: 'Phe Tôi', ... }
   };
   ```

2. **Add English overlay** in `src/i18n/content.en.json`:
   ```json
   { "civ": { "MyFaction": { "name": "My Faction" } } }
   ```

3. **Call via typed wrapper**:
   ```typescript
   import { civName } from '@/i18n/content-wrappers';
   return <h1>{civName('MyFaction')}</h1>;
   ```

---

### Case 3: Narrative Copy (Dialog, Tutorial)

A new quest dialog, tutorial hint, or NPC speech.

1. **Call `tContent()` at render time** (never at module top-level — language changes at runtime):
   ```typescript
   import { tContent } from '@/i18n/content-localization';
   
   function DialogStep() {
     const dialog = tContent(
       'dialog',
       'kael-rescue',
       'greeting',
       'Hello, friend!',  // EN inline fallback
     );
     return <p>{dialog}</p>;
   }
   ```

2. **Add translations** to both `content.en.json` and `content.vi.json`:
   ```json
   // content.en.json (if VN-authored, EN overlay)
   { "dialog": { "kael-rescue": { "greeting": "Hello, friend!" } } }
   
   // content.vi.json (VN overlay)
   { "dialog": { "kael-rescue": { "greeting": "Xin chào, bạn!" } } }
   ```

3. **Key naming**: `<category>.<storyId>.<fieldName>` — e.g., `dialog.tutorial.opening`, `tutorial.build.hint-1`, `narrative.intro.voiceover`

---

### Case 4: Status/Enum Label

For member states, mission states, equipment rarities, etc., where the UI label is keyed off a data value.

1. **Add key to ui.en.json and ui.vi.json** using the enum value as the sub-key:
   ```json
   // ui.en.json
   { "status": { "idle": "Idle", "on-quest": "On Quest", "injured": "Injured" } }
   
   // ui.vi.json
   { "status": { "idle": "Rảnh", "on-quest": "Trong Nhiệm Vụ", "injured": "Bị Thương" } }
   ```

2. **Call in component**:
   ```typescript
   const { t } = useTranslation();
   return <span>{t(`status.${member.status}`)}</span>;
   ```

### Testing & Coverage

**Run before commit**:
```bash
npm run test
```

**What it checks**:
- `ui-parity.test.ts`: Ensures `ui.en.json` and `ui.vi.json` have identical key structure (708 keys each). Fails if misaligned.
- `content-coverage.test.ts`: Ensures every EN-authored entity (`missions`, `items`, `enemies`, `equipment`, `furniture`, `facilities`, `recipes`, `ranks`, `archetypes`) has a Vietnamese entry in `content.vi.json`. Ensures every VN-authored entity (`civ`, `skills`) and the `role` field have entries in `content.en.json`.

If a test fails, the output lists missing keys. Add them to the respective JSON file and re-run.

## Known Considerations & Open Items

1. **Number formatting locale awareness**: Currently uses browser locale (.toLocaleString()); no language-aware switching implemented. User decision pending on whether to enable `toLocaleString('vi-VN')` for VI players and `toLocaleString('en-US')` for EN.

2. **RTL support**: Not implemented. WORLDSCOLIDE uses LTR layout.

3. **Plural forms**: i18next interpolation supports pluralization via `t('key', { count })`, but no game strings currently use it. Can be added per-string if needed.

4. **Date/time localization**: Game clock displays raw seconds/minutes; no human-readable date/time localization needed at this stage.
